# 交付说明

给实施与验收看的一页。写的是**这套系统现在能做什么、不能做什么**，
以及上线时必须做的事。功能清单见 `delivery-plan.md`，部署步骤见 `deployment.md`。

---

## 一、必须先跟客户对齐的三件事

这三条不是"待优化"，是**交付时会被问到、答错就变成纠纷**的事。

### 1. 证件与回单的 OCR 没有接

界面上有"识别"这条链路，状态机、字段、展示都在，但**没有接任何一家 OCR 引擎**。
上传证件或回单之后，状态是「待人工」，信息需要人工录入。

配了 `OCR_PROVIDER` 也没用——目前只会把提示文案从「未配置」改成
「引擎 X 尚未接入实现」。真正接入要在 `recognizeReceipt` /
`applyCredentialOCR` 里实现具体厂商的调用，是一个单独的集成项。

**如果验收标准里含「自动识别」，必须单独排期，不是配个环境变量就能开的开关。**

无引擎时系统**刻意不伪造**签收人和签收时间——回单是 e-POD 法律凭证，
也是财务自动核销的依据，凭空造一个"识别出来的"签收人，等于制造签收证明。

### 2. 多副本部署必须先接对象存储

默认 `MEDIA_BACKEND=local`，媒体文件（头像、证件、打卡照、回单、合同）
写在容器本地盘。**单副本没问题，起两个副本就会间歇性丢文件**：
上传落在 A 的盘上，下一次读被路由到 B 就 404。

这个故障预发（通常单副本）复现不出来，会一路活到生产扩容那天。
配置见 `deployment.md`「媒体存放」。

已有文件迁移的顺序是**先同步后切换**——反过来的话，切换到同步完成之间
上传的文件会留在旧副本的本地盘上，之后再也找不到。

### 3. 对账单归集的查询会随费用记录总量线性变慢（暂不用管，但要知道）

生成对账单时归集费用的那条 SQL，实测过一次：

| 费用记录总量 | 生成一张对账单耗时 |
|---|---|
| 31 条（演示数据） | 0.4 ms |
| 20 万条 | 46 ~ 53 ms |

慢的原因不是数据量本身，是**查询的起点选错了**：执行计划先按
`direction='receivable'` 捞出全部应收（20 万里的 10 万条），
再逐条回表去查那张运单是不是这个客户的（实测回表 34,622 次）。
也就是说，给 A 客户出账要把**所有客户**的应收都过一遍。
另外 `occurred_at` 上没有索引，而账期条件写成
`(occurred_at AT TIME ZONE 'Asia/Shanghai')::date >= …`，
把列包在函数里，就算加了索引也用不上。

**为什么现在不改**：50ms 对一个每月按客户跑几次的批量动作完全够用，
而它在钱的路径上——发布前动执行计划，风险大于收益。
按上面的斜率，百万级费用记录时大约 250ms，仍在可接受范围；
真正需要动的时候，方向是让查询从「这个客户的运单」起步，而不是从
「所有应收」起步。

### 4. 定时任务在多副本下会各跑一份

进程内的削峰、掉线扫描、指标物化等任务，每个副本都会跑。
它们是幂等的，不会算错账，但会有重复的日志与无谓的库压力。
要精确控制得拆成单副本的 CronJob。

## 二、上线当天必须做的

- [ ] `.env.prod` 里所有密钥与口令换成强随机，且不在版本库里
      （`DJANGO_SECRET_KEY` 同时签发内部令牌与司机端令牌，
      配错在测试环境永远不会暴露）
- [ ] 用 `/app/adminctl` 开第一个超管，登录后**立刻改掉命令行里用过的口令**
      （命令行参数会进 shell history 与进程列表）
- [ ] 跑过 `seed` 的话，删掉 `seed_*` 四个演示账号——它们是公开的弱口令
- [ ] 确认 `DJANGO_CORS_ORIGINS` 是真实前端域名，不是 `*`
      （配成 `*` 时网关会拒绝启动）
- [ ] 前置网关终止 TLS，80 跳 443
- [ ] 备份跑起来，并且**至少完整演练过一次恢复**
- [ ] 按 `deployment.md`「对公开放的面」确认三个限流变量已配

上线前在目标机器上跑一遍 `scripts/dev/release-check.sh`，
它会明确区分「通过 / 失败 / 跳过」，并列出机器判不了、必须人工确认的几项。
**跳过不等于通过。**

## 三、对公开放的面（安全相关，实施必读）

不需要登录就能打到的业务端点共 7 个。司机端五个各自校验司机令牌；
`/track`（公开查单）和 `/public/orders`（客户自助下单）是真正对公众开放的。

`/track` 的校验是「订单号 + 手机号」，而手机号允许后 4 位匹配
（客户常只记得后四位）。这是可用性取舍，**其安全性依赖限流**：
没有限流时，实测穷举 10000 种四位组合只要 60 秒。
默认已配两道闸（按订单号、按来源 IP 且只对失败计数），
想更严可调 `THROTTLE_TRACK_ORDER`。

上线后应观察 `/metrics` 上 `route="/api/v1/track"` 的 404 与 429 数量，
持续升高就是有人在扫。

## 四、这套系统当前**不**做的事

说清楚边界，比事后解释省事：

| | 说明 |
|---|---|
| OCR 识别 | 见上，未接入 |
| 电子签章 / CA 认证 | 合同可生成 PDF，但没有第三方签章 |
| 财务凭证对接 | 对账在系统内闭环，未对接金蝶/用友等 |
| 税务发票 | 不开票、不对接税控 |
| 多币种 | 只有人民币 |
| 移动 App | 司机端是网页（`/driver`），不是原生 App |
| 实时定位 | 依赖终端上报（MQTT / HTTP），系统本身不采集 |

### 后端有接口、管理端没有界面的几块

这些不是缺陷，是发布前有意识地不做。列在这里是为了**被问到时能答上**，
而不是让实施自己撞上。想用的话每一块都要单独排期。

| | 现在怎么办 |
|---|---|
| 车联网：设备 / 地理围栏 / 告警 | 后端增删改与告警确认、关闭都有；轨迹展示有界面。**配置与告警处理没有界面**——系统本身不采集定位，没有数据源时做配置页是空转 |
| 框架合同（合同价） | 计价规则支持挂在合同上做更精确的匹配，但合同没有管理界面。**报价实际走的是按客户 / 线路通配那条**，够用；要用合同价需单独排期 |
| 跨运单的付款申请队列 | 付款申请由报销审批自动生成，**付款动作在运单的报销面板上**，闭环是通的；缺的是"所有待付款"这样一张跨运单的清单 |
| 对外推送（Webhook） | 推送配置与投递记录只能走接口，没有配置页 |
| 部门层级 / 员工组 | 员工的组织归属在「员工名录」里选；独立的部门树与员工组没有界面，授权走角色 |
| 线路主数据 | 线路名在订单与计价规则里直接填，没有线路字典页 |

这张表由 `scripts/dev/reachable-actions.py` 盯着：后端加了一块没有界面的功能，
要么补界面，要么在那个脚本里写明为什么不做——写不出理由的，多半就是漏了。

## 五、已知的、有意为之的取舍

- **表格行操作默认半透明，悬停才显现**——为了让密集表格不被按钮淹没。
  代价是可发现性，新用户需要被告知一次。
- **中止运输必须填原因**——中止后面跟着费用争议和责任认定，
  没有原因事后无法还原现场。这一条会挡住"随手中止"。
- **发车后不能作废，只能中止**——车已经开出去过、人和车被占用过，
  作废的语义是"当它没发生过"，不适用。中止会保留记录并强制走一次结算。
- **自助注册默认关闭**——账号应由管理员在「组织与权限 → 员工名录」开通，
  开出来就带组织归属与角色。需要对外客户门户自助开户时才置
  `TMS_ALLOW_SELF_REGISTRATION=1`。

## 六、验收前建议实跑的一条链

用真实数据走一遍，比看功能清单有用：

1. 客服工作台建一单（填真实的起止地与货物）
2. 订单管理里能搜到它
3. 调度工作台派给一个承运商，生成运单
4. 运单流转到签收，上传一张回单——**传完点开「查看原件」，确认图打得开**
5. 对账中心生成对账单、核销
6. 用 `/track` + 该单的手机号在浏览器上查一次
7. **用手机打开 `/driver`**，用那个司机的手机号 + 身份证后 6 位登录，
   给同一张运单打一次卡——**权限弹窗那一下故意不要点「允许」**
8. 把库和 `media/` 一起备份，删掉，恢复，**再打开那张运单看回单图还在不在**

第 4 步那句「点开确认」不是客套。发布前这三条上传路径查出来四个问题，
全都返回 2xx 或看起来正常，只有真去点开才发现不对：
订单附件读了文件名把字节丢了、回单和证件因为前端发 multipart 而后端只解
JSON 直接 400、存下来之后链接又绑错了字段成了死链、以及附件在详情接口里
被写死成空数组所以页面上一直显示「暂无附件」。
凭证类功能的验收标准只有一个：**传上去之后点开，看到的是你刚传的那张。**
接口返回 201、列表里出现那一行、都不算数。

第 7 步要用真手机、且**要在不给定位权限的那一侧走一次**。司机端是另一套界面、
另一套鉴权（`X-Driver-Token`），发布前第一次真按下去查出两个洞，两个都让它在
生产上完全不能用，而两个在管理端都看不出来：跨域部署时预检没放行那个头，
登录之后是一片空白（服务端日志一行都没有）；以及司机不点定位权限时，
打卡按钮永久停在「正在定位…」，那个司机从此再也打不了卡。
不点「允许」是司机的常态，所以验收也要按常态走。

**前端与网关不同源部署时**（前端上 CDN、或单独一个域名），
司机端会带一个自定义请求头。这条现在由代码保证并有用例钉住，
但如果中间还有一层自己配的反向代理/WAF，要确认它没有把预检响应头改掉——
症状就是上面那个"登录成功之后一片空白"。

第 8 步是最容易被跳过、也最要紧的一步：只恢复库的话，对账单还在，
但作为凭证的回单照片指向了不存在的文件——账对不上还拿不出证据。

这几条现在**都在 CI 里跑**（`browser` 这个 job：真起库 + 网关 + 前端构建产物，
用真浏览器按一遍）。此前它们只在 `release-check.sh` 里，也就是只有人想起来跑时才跑——
而发布前查出来的严重问题几乎全是这批检查抓到的，编译、单测、静态走查一个都发现不了。
CI 里前端用构建产物单独起、和网关不同源，这正是生产上前端单独部署的形态。

脚本清单：`scripts/dev/write-paths.mjs` 走真浏览器把三条
上传路径各传一次并点开比对，`scripts/dev/driver-walk.mjs` 在手机视口、
**不给定位权限**的条件下把司机端走一遍并回库核对照片，
`scripts/dev/backup-drill.sh` 演练备份恢复并真的取一个媒体文件。
三个都接进了 `release-check.sh`。
