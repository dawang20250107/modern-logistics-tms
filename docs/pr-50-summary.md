发布前：把「按下去到底发生了什么」逐个走了一遍

起点是「不加功能，把钱这条线上的洞补上、再织一张网」。做完之后回答
「离发布还差什么」，一条条推完。

**86 个提交，223 个文件，+21651 / −858。Go 用例 13 → 203，前端 89，10 个包全部有测试。**

前半程（一～七）是补洞与织网；后半程（八～十一）是发布前的四轮走查，
每一轮换一个问法：

| | 问的是什么 | 挖出的典型 |
|---|---|---|
| 八 | 真按下那个按钮，回库里核对到底发生了什么 | 上传成功但字节丢了、导出把一页说成全部 |
| 九 | 按钮压根不存在的地方，怎么按 | 阶梯价没有输入框、异常闭环只有上报没有关闭 |
| 十 | 两个人同时按会怎样 | 800 元赔付被计成 4800，六次全返回 200 |
| 十一 | 换一个受限角色，他的一天是什么样 | 「主数据查看」能导走全库 5 万单 CSV |

这四轮挖出的问题比前半程所有静态审查加起来还多，
而且**没有一个是靠读代码能看出来的**。

## 一、补洞

### 财务域完全没有鉴权（实测，不是读代码猜的）

拿一个刚 `/auth/register` 出来的账号（`is_superuser:false`、`permissions:[]`）
挨个打接口：

| 端点 | 修复前 | 修复后 |
|---|---|---|
| `GET /finance/statement-overview` | **200**，`net_position: 129,413.33` | 403 |
| `GET /finance/aging` | **200**，逐客户账龄 | 403 |
| `GET /finance/statements` | **200**，整本对账台账 | 403 |
| `POST /finance/statements/{id}/settle` | **404**（不是 403） | 403 |

最后一条最要命：404 意味着请求压根没被鉴权拦住，只是那个 UUID 不存在——
换成真实单号，这个账号就能把别人的钱标记成已收。

### 其余三处

- **权限点目录只有 3 行，代码却校验 12 个**。差额那 9 个在权限矩阵界面上
  没有勾选框，任何角色都无法被授予。整套 RBAC 退化成「超管或什么都不能干」。
  3 → 17。
- **令牌永不失效**。refresh 轮换不作废旧券、改密不踢会话、退出登录在服务端
  是空操作。补了按 jti 精确吊销 + 账号级水位线。
- **自助注册默认关闭**。上面那个财务洞正是靠它拿到的已认证身份打进去的。

## 二、织网

Go 侧此前 23,498 行代码配 13 个用例，且**没有一个 HTTP 层测试**。

**鉴权矩阵**（155 条路由）第一次跑就抓出三处同类漏：`/waybills/stats`、
`/orders/funnel`、`/workbench`（`pool_top` 给的是完整订单记录）。

**钱的回归网**：计价 17 条（含阶梯价边界 5 吨取哪一档，决定收 1300 还是 1100），
对账 5 条，每条对着一个历史上真实算错过钱的 bug。

## 三、上线准备

| | 问题 | 处置 |
|---|---|---|
| HTTPS | `nginx.conf` 只有 `listen 80`：JWT、口令、回单照片全部明文过网 | 443 + TLS1.2/1.3 + HSTS |
| 验证码 | 只写进日志，接口却回 `sent:true` | 未配通道则 `sent:false`，明确提示 |
| 进程内状态 | 登录锁定、限流、验证码都在内存里，多副本换个副本就绕过去 | 落库共享。限流/锁定失败**放行**，令牌吊销失败**拒绝** |
| 配错能跑 | 弱密钥、占位密钥、CORS `*` 都能启动 | 生产模式下一律拒绝启动 |
| 探针 | 只有恒回 200 的 `/healthz` | 新增 `/readyz` 查库；`/healthz` **刻意不查** |
| 备份 | 从没演练过 | `backup-drill.sh`：备份→删库→恢复→**真的起网关、真的 GET 一个媒体文件** |

## 四、真实数据量暴露的一整类问题

此前所有验证都在十几条演示数据上做。造出 5 万单之后：

**性能**：① 连接池是 pgx 默认值 4，成了整个网关的吞吐天花板（实测 221 QPS）；
② 「今日建单」把列包在函数里，索引失效，32.8ms → 0.41ms；
③ 列表先关联后分页，深翻页 212ms → 15ms。
**净效果：吞吐 221 → 365 req/s，p95 124 → 87ms。**

**「把一页当全量」四处**：调度工作台最严重——三个池各拉 20 条，计数、搜索、
"仅看紧急"全在前端对着这 20 条做。真实数据下订单池 8336 条：顶部写
「待派 20」实际 8336、「紧急 40」实际 1389。登录审计更不该出现：
528 条(402 次失败)时界面写「100 条 · 失败 80」，把爆破痕迹显示成"看起来还好"。

**一单没送到的货被算成了准点交付**：状态机里 `departed`/`in_transit` 没有任何
出口，车发了之后要终止只能先记一次**没发生过的到达**，而准班率按 `arrived_at`
取样。根因是同一套 SQL 有三份拷贝。

# 八、真按下那个按钮

前面所有检查——tsc、后端用例、浏览器冒烟、鉴权矩阵——有一个共同盲区：
**它们都不点按钮**。

## 点下去就是死的：三段功能完全够不着

- **对账中心的「生成对账单」恒定 400**。前端发 `period_start`，后端结构体上是
  `json:"start"`；同一个请求里 `external_total` 前端发数字 `0` 而后端是
  `string`——**一个数字就让整个请求体解不开**，报错还是「请求体不是合法 JSON」。
- **「承运合同」整段从界面上够不着**：前端三个 mutation 写好了却没被渲染，
  后端那条路由又只有 GET。
- **「司机报销」同样写好了不渲染**：过路费、油费是司机先垫的钱，
  没有入口意味着进不了系统。

## 凭证上传：三条路径，四个问题，全部返回 2xx

1. 订单附件读了 multipart 里的**文件名**，把字节丢了，而 toast 说「附件已上传」。
2. 回单和司机证件直接 400：前端发 multipart，通用 CRUD 引擎只解 JSON。
3. 存下来之后链接是死的（页面绑的是外链专用字段）。
4. 附件在详情接口里被写死成空数组，传成功了页面也永远显示「暂无附件」。

补完还漏一个：`self_uploaded="false"` 在 multipart 里是字符串——
**第一版用例只传必填字段，绿的，而页面照样 400**。

## 导出：把一部分说成了全部，四处

服务端写死 `LIMIT 5000` 且悄悄截断（5 万单导出 5000 条）；订单台账的
「导出全部」一个筛选条件都不带；`hideExport` 只挡住了 CSV 那颗；
审计/调度池/对账单只导当前页。→ 上限 50000 并**在 CSV 最后一行写明截断**，
导出跟着筛选走，取不到全量的按钮直接写「CSV(本页)」。

## 「再点一次会怎样」——四处，都在钱和凭据上

| | 重复调用的后果 |
|---|---|
| 代收货款 | 收款时间戳被改晚——现金纠纷时唯一的凭据 |
| 承运合同 | 一次点击把司机**已确认**的合同改判成"已拒签" |
| 报销审批 | 并发下靠付款申请单号的唯一索引**碰巧**拦住，代价是两个 500 |
| 异常关闭 | **直接多生成应付：800 元的赔付连关三次变成 2400** |

共同点：这四个动作都绕开状态机自己写守卫，而守卫都只想到了"上一步做没做"，
没想到"这一步做过没有"。走状态机的动作反而全是安全的。

## 货量守恒

| | 实测 |
|---|---|
| 订单拆单 | 未分组的明细留在随即作废的原单上：60 件 → **30 件** |
| 订单合单 | 无明细行时表头照抄第一张：3+7 件 → **7 件**，而这是 99.9% 的订单形态 |
| 运单拆单 | 子单货量由调用方给且不校验：少给丢货，多给**运费翻倍** |

## 配置：设了不生效

**SMTP 五项全错名**（模板 `TMS_SMTP_*` vs 代码 `SMTP_*`）——运维照模板全填好、
重启，邮件一封发不出去。**地图 Key 名字和位置都不对**，而且
`Dockerfile.frontend` 一个 `ARG` 都没有——按文档部署，地图**没有任何办法配得上**。
**令牌有效期写死** 30/7 而模板里一直有那两项。

## 免登录的面

`/track` 的"密码"只是手机号后 4 位、订单号顺序可猜，且**没有任何限流**——
实测 100 次尝试 609ms，一万种组合 60 秒穷举完。司机登录那道按 IP 的闸两头都不对：
换 IP 就重置（挡不住爆破），同出口第 11 个司机**登录成功**也被 429
（车队早上集中上线互相挤掉）。

## 演示数据本身的坑

**5 个演示司机身份证号全是空串**，而司机端登录要「手机号 + 后 6 位」——
验收时客户点开司机端，用哪个司机都是"不匹配"。**演示账号没有员工档案**，
「员工名录」是空的。**4168 张订单是 `dispatching` 但没有锁定人**
（造数只写状态不写 `claimed_by_id`）——它们在「待分配」里看得见，
点「锁定」恒定 409，占池子的一半。

# 九、功能写好了，界面上够不着

第八节的方法是"真按下那个按钮"。这一节的问题是：**按钮压根不存在的地方，怎么按？**

这一类缺口出现了 **八次**，全都不报错、不崩、类型检查也过，页面看起来正常，
只是少了一块——而少的那块没人知道它本该在。逐页点按钮也发现不了。

| 缺的那块 | 后果 |
|---|---|
| 承运合同的三个 mutation（写好了没渲染） | 整段功能够不着 |
| 司机报销（同上） | 司机垫的过路费油费进不了系统 |
| **计价规则的阶梯价** | 表单默认就是「按重量阶梯」，而没有一处能填那几档价 → 存下来 `tier_prices` 是 `[]`，算价时单价取 0，**用户认真配的合同价报出来是零，而且不报错** |
| **异常闭环的后半截** | 指派/处理/定责关闭四个端点全的，界面只能上报 → 异常永远停在「待处理」，**而关闭正是定责那一步**，赔付永远进不了账 |
| **承运商拉黑** | 表格有「黑名单」标签、筛选器有这一档、详情显示「黑名单：是（原因）」，唯独没法设上或撤掉 |
| **登录解锁** | 连续失败会锁账号，而管理员在系统里解不开——只有闸没有钥匙 |
| 录单的「来源明细」 | 状态里有、提交时带上、后端存下来，连每个渠道的占位符文案都写好了，就是没有输入框 |
| 计价规则的费用科目 | 科目写死成 `"FREIGHT"`——**后端两份词表里都没有这个码**，钱落进一个谁也不认识的科目 |

## 司机端：第一次被真按下去

此前四个浏览器走查全都从管理端 `/login` 进去，**一个都没打开过司机端**。
第一次按就停在第二步：

- **预检没放行 `X-Driver-Token`** → 跨域部署时登录 200、之后一片空白，
  界面只写 "Failed to fetch"，**服务端日志一行都没有**。
  同源部署不触发，预发多半复现不出来。
- **司机不点定位权限，打卡按钮永久卡住**。`getCurrentPosition` 的 `timeout`
  选项不覆盖授权那一段：实测未授权/未答复弹窗时 15 秒两个回调一个都不来。
- 打卡照片路径写死成 `<运单号>_<节点>.jpg`，**同节点重试一次就原地覆盖**。

## 检查自己说谎的三处

**一条检查失败时说的原因必须是真的。**

- `ui-audit` 在网关没起时把**登录页**当六个业务页各量一遍，报出
  「点击目标过小」——假红。
- `smoke-ui` 同样条件下报**绿**：请求在网络层就断了，`page.on("response")`
  不触发，"10 个页面无异常"而它一个都没打开过。
- `backup-drill.sh` 里 `find | head -1` 在 `pipefail` 下吃 SIGPIPE，
  **媒体目录攒到 145 个文件那天**才第一次复现，报「演练失败」而备份恢复全是好的。

八个走查脚本现在共用一套退出码：`0 过 / 1 有发现 / 2 没跑起来`，
而 `2` 记「跳过」不记「失败」——把跑不起来记成失败，几次之后大家就开始无视这一项。

# 十、两个人同时按同一颗按钮

前面九节都是单人视角。

后端有一类写法——先 `h.DB.QueryRow` 读一次状态做前置校验，通过了再
`h.DB.Exec` 写。两条语句之间没有锁、没有事务，UPDATE 也不带状态条件。
串行点两次会被第一条挡住，看起来是好的；并发就一起穿过去。

| | 实测 |
|---|---|
| 6 个并发关闭同一条异常 | **6 个都返回 200**，落 6 条应付，800 元的赔付计成 **4800** |
| 审批与驳回同时发生 | 审批已落应付和付款申请，抢输的驳回照样把状态覆盖成"已驳回"并返回 200 —— 账上挂着一笔已驳回却仍要付的钱 |

两处都改成 `Begin + SELECT … FOR UPDATE`。配套 `scripts/dev/txn-guard.py`
扫全部 157 个 handler 找这个写法，确实无害的 7 处（幂等的提醒确认、
只改状态不生成单据的对账单确认与异常指派/处理、后写覆盖即正确语义的
回单核验与外部付款回写）逐条写了理由。

**顺带挖出对账单那条**：资金不变量用例在演示库上红了 4 条，追下去发现
237 张对账单里 **235 张是空的**。两个来源——`GenerateStatement` 没有
"一条明细都没有就别建单"的判断（空账期点一下就产出一张有正式连号单号的空单，
财务得去作废并解释）；以及用例和走查脚本自己在留垃圾：清理语句先是列名写错
（`counterparty_ref` 不存在），改对后又发现 `counterparty_id` 是 varchar、
`$1::uuid` 比不了，两次都被 `_, _ =` 吞掉，**删除从来没生效过**。

# 十一、换一个受限角色，他的一天是什么样

前十节所有走查都用 **admin 跑，而 admin 带 `*` 权限——它永远看不到 403 长什么样**。

## 一、读的那一面从没系统扫过

写动作那 100 条早就逐条打过了，读这一面一直没有。而它才是数据泄漏的入口：
一次请求带走的是整张表。

探针账号：角色只勾「主数据查看」（听起来只是看客户和司机档案），
数据范围给「全部」——客服/调度岗上很常见的配法。

| 端点 | 实测 |
|---|---|
| `GET /orders` | 200，全库订单 |
| `GET /orders/export` | 200，**5.26 MB、50002 行 CSV**（客户名、始发目的、报价） |
| `GET /orders/funnel` | 全库漏斗 50839 单及各状态分布 |
| `GET /workbench` | `pool_count=4588` + `pool_top` 五条完整订单记录 |
| `GET /exceptions` | 异常记录，含责任方、赔付金额、处理结论 |
| `/orders/{id}/workflow`·`/timeline`·`/lineage`·`/dispatch-suggestion`·`/ymm-quote` | 各阶段时间、拆并单血缘、推荐承运商、市场报价区间 |
| `GET /carriers/{id}/performance` | 成交量 1538、异常率、常跑线路 —— 而承运商**列表**是要 `carrier.view` 的 |

三处根因各不相同：订单域 9 条读路由压根没挂闸（`Funnel` 那条把权限点传了
空串，而空串在 `Guard` 里就是"不设限"）；工作台的 `finance` 块判了
`finance.view`、`dispatch` 块没判，同一份数据换个入口就出来了；异常列表则是
`main.go` 里的自实现路由**覆盖掉**了通用 CRUD 已经挂好闸的那条。

新增的走查把 **78 条无参数 GET + 64 条带参数 GET 全部覆盖，一条不跳过**。
带参数那些用不存在的 UUID 也能判——挂了闸的路由在查 ID 之前就 403，
没挂闸的才走到查库返 404，**403 与 404 的差别正好就是"有没有闸"**。

## 二、文档写的验收链，用文档给的角色跑不通

第七节验收链第一步是「客服工作台建一单」，而演示的「客服」角色只有
`waybill.view`，下单要 `waybill.manage` —— 实测 403。工作台还挂在侧栏上，
表单能填满，**在提交那一下才拒绝**。

直接给 `manage` 又太多（那会连派单、签收、代收货款打款、异常定责一起给出去），
所以拆了一个只管"把单子录进来"的 `waybill.create`。

补上权限后第一次真按下去，撞出第二个洞：

```
HTTP 500  建单失败：ERROR: value too long for type character varying(32) (SQLSTATE 22001)
```

七个字段都是这一句，**而且不说是哪个字段**。改成建单前按 `information_schema`
里的真实列长校验（不硬编码，列改宽了校验跟着改），400 + 中文字段名 +
上限和实际长度；原始 SQL 错只进日志。

## 三、派出去的运单没有组织归属

拿客服（数据范围=本网点）真的点：它在「订单管理」里看得见自己建的单，
点开对应运单是「**运单不存在、无权访问**」。

根因不是权限——`ops_waybill.organization_id` 决定运单的数据范围，而主派单路径
和批量派承运商**压根没写这一列**，落成 NULL 就只有「全部」档看得见。
转承运那条路径倒是写了。同一个字段，三条路径两种行为。

统一到「归属取建单人的组织」：中心调度替各网点派单是常态，按派单人算会把
网点自己的单子划走。顺着扫了所有带 `organization_id` 的表，批次对账单同样
漏写——生成它的人自己在对账中心都找不到它。

这一类的可怕之处是**不报错、不崩、类型检查也过**：表现只是"某些人看不见
某些数据"，而看不见的人多半以为是自己权限不够，不会来报。

## 四、看得见按不动的按钮

后端每条写路由都挂了闸，所以点下去只是弹一句"无权限"。但对操作的人来说，
一屏可点却点不动的按钮就是"系统坏了"——他会重试、问同事、提工单，
而没有一处告诉他缺的是哪个权限点。

| 角色 | 看到的写按钮 |
|---|---|
| 财务（只读） | 对账台账五个「确认」两个「核销」、「批量审计」「+ 生成对账单」；计价规则的「新增/编辑/删除」和启用停用开关 |
| 客服（只有查看权） | 订单管理的「确认」「进池」和整条批量栏；调度台的「锁定」「派单」「智能排线拼单」；**运单详情上 12 处写动作与超管逐字相同** |
| 只有 masterdata.view | 证件上传的文件框——选完文件才 403，而那时人已经把证件照片挑出来了 |

派单弹窗有四个入口（派单按钮、精准派单、查看轨迹、列表上的双击与回车），
前两个按权限藏了，后两个藏不掉——在 `openWb` 里统一兜住，比逐个入口加判断可靠。

驾驶舱对所有角色开放，里面的财务敞口和证件预警两块却要对应权限：
原先照发不误，客服/财务一进首页就吃 403，磁贴上写着「财务数据暂不可用」
加一颗重试按钮——读起来像系统故障，实际是这个角色本来就看不了。

命令栏那处更隐蔽：`aiReady = aiStatus.data?.configured !== false` ——
请求**失败**时 `data` 是 undefined，`undefined !== false` 为真，判成"可用"。
没有 `ai.use` 的账号看到 AI 入口亮着 `Enter ↵`，按下去才 403。
而那段代码上面自己的注释写的正是「要在用户按下去之前就告诉他」。

## 豁免名单：一条写错的理由，能把一条路由藏到发布之后

「后端有这个动作、界面上够不着」这条检查靠一份豁免名单撑着。这一轮
去逐条核名单里的理由，起因是车载上报那两条：豁免写的是"走设备/网关
凭据，不走用户权限"，而它们既没有设备凭据、也不在设备侧的路由组上。
**理由是假的，于是那条路由再也没有被任何检查看一眼**——这比没有名单
更糟，因为名单会让人觉得"这里已经想过了"。

给四份名单都加上自检（豁免过期 / 名单里的条目已不存在）之后，
`reachable-actions.py` 立刻报了两条"前端已经在调了"。**去查，是假阳性**：
它把整个前端拼成一个大字符串，看路径的最后一段和它前面那段分别出现过
没有——这两次出现可以来自毫不相干的两个文件。车联网告警的 `ack` 来自
司机端的提醒确认，`"alerts"` 来自承运商列表里一个叫 alerts 的表格列。

改成逐条比较整串路径之后，漏报那一侧露出来两条，都是真的：

**回单核验（`POST /receipts/{id}/confirm`）前端一次都没调过。**
运单详情的回单区只有上传、看原件和一个 OCR 徽标，连每张回单自己是
"待核验/已核验/已驳回"哪一档都不显示。界面上唯一能动回单状态的地方，
是运单列表那个批量「标已回收」——它直接把运单写成 `returned`，
不看下面挂的是哪张回单。库里就是这个样子：运单 LT-000002516 显示
"回单已回收"，而它下面五张回单**全都还是 uploaded**，一张都没人核过。
而结算认的是 `audited`，只有逐张核验通过才到得了。

驳回那半边完全没有入口。后端是按"这张运单还有没有通过核验的回单"
重算的：核验通过 → 运单 `audited`，改判驳回 → 退回 `returned`。
没有这颗按钮，一张错核的回单就再也退不回来，运单会一直挂着
"凭证齐全"等着放款。界面补上了，实测两个方向都通。

另一条 `POST /ai/deepseek/chat` 是平移自 Django 的裸 LLM 透传，
产品的 AI 入口是 `/agent/chat`，登记进名单。

顺带治了另一种会过期的理由：有几条豁免写的是"界面走的是另一条"。
**这句话本身会失效**——那条替代路径哪天没人调了，就从"有等价入口"
变成"两条都够不着"，而名单还在说没事。替代路径改成写进 `INSTEAD`
由检查自己去核，而不是写成一句话让人去信。

## 方法：每一条新检查都拿修复前的代码回测过

没做过这个回测的检查不能信——绿的可能只是因为它什么都抓不住。
这一轮几处**我自己先被判红**：

- 想用扫源码一次盖住三份状态词表拷贝，**三个写法全不成立**——
  抓不住真问题的检查比没有更坏，删了改成行为测试
- 导出全量的翻页：页大小要了 500 而服务端夹到 200，"拿回来的比要的少就是
  最后一页"于是第一页就停——**8367 条只导出 200 条，和它要修的问题一模一样**
- 接口对齐走查加进 CI 后 0 秒失败——漏了 `working-directory`，
  看起来像"抓到问题了"，其实是检查自己没跑起来
- 并发核销用例 6 个并发只有一半运行能复现，**一条只有一半概率变红的并发用例
  等于把问题留给运气**，改成 12 个
- `role-walk` 的按钮扫描把**页签**「收付款核销」当成了写按钮，一直报"只读角色
  看得见核销"——**报错原因不对比不报更伤**，修的人会去改一个没坏的东西
- `write-needs-perm` 的豁免名单里，我按印象写的三个文件**根本没有写请求**，
  被名单自查逐个指出。名单里塞着不相干的条目，下次读的人就会以为"这些是有意
  豁免的"——豁免名单一旦不可信，整条检查就废了
- `orgcolumn` 检查第一版只看字面量，把 `` `+waybillCopyCols+` `` 拼出来的
  运单拆/合两处**误判成漏写**。先展开同包常量再判
- 用例清理里用了 `t.Context()`：它在 `Cleanup` 之前就被取消，删除全是
  "context canceled"，而 `_, _ =` 把它吞了——这正是那 235 张孤儿对账单的同类成因
- 反方向那条检查第一版**手写了一串"该有的按钮名"**，其中「生成合同」在那张
  运单上对**所有人**都不显示（合同已是"已确认"）——超管也没有。
  检查报的原因是假的。改成跟超管在同一张运单上对照，
  差异逐条按权限点写明理由，顺便自带空转防护：超管都没有按钮就说明页面没打开
- 回单核验那条前端用例，第一版断言写的是 `toContain('status: "confirmed"')`。
  把整块按钮删掉**它照样绿**——mutation 的类型签名里就有
  `status: "confirmed" | "rejected"` 这段字符。那查的是"有没有人写过这个
  mutation"，恰恰漏掉这条检查要防的那件事：按钮被改版删掉、mutation 留在
  原地。断言改到按钮的调用点上，回测确认删掉按钮就红
- 收紧路径匹配之后又冒出四条"豁免过期"，**还是假阳性**：前端把动作名写成
  变量（`` `/orders/${id}/${action}` ``），规整完是 `/orders/{}/{}`，
  段数对得上就配上了 `/orders` 下的每一条三段路由。改成那个词必须在同一个
  文件里以字符串出现过才算数——即确实有调用点把它传进去

## 量过之后决定不改的地方

对账归集的 SQL 里 `(occurred_at AT TIME ZONE …)::date >= …` 把列包在函数里。
造了 20 万条费用记录量：31 条时 0.4ms，20 万条时 46~53ms。真实原因也不是那个
函数包裹，而是**查询起点选错**——先捞全部应收再逐条回表查客户（回表 34,622 次）。
**没有改**：50ms 对每月跑几次的批量动作够用，发布前在钱的路径上动执行计划
风险大于收益。数字和方向写进了交付说明，下一个人拿到的是测量结果而不是猜测。

同样量过之后不改的还有：轨迹接口的载荷（2880 个点 279 KB）、
车联网的管理端界面、按合同维度的计价、跨运单的付款队列。
