# 界面审计：为什么现在这套不够专业

用 `scripts/dev/ui-audit.mjs` 在 1680×1000 下量的，不是看着觉得。下面每条都有数字。

## 基线数字（改版前）

| 页面 | 首屏数据行 | 行高 | 壳高 | 壳占比 |
|---|---|---|---|---|
| 订单管理 | 17 | 40px | 282px | 28% |
| 调度工作台 | 2 | 54px | 395px | 40% |
| 计价规则 | 4 | 56px | 542px | 54% |
| 驾驶舱 | — | — | — | 指标带 231px |

壳子构成（亮色）：

```
订单管理    topbar=58 stats=42  toolbar=64 tableHead=34
调度工作台  topbar=58 hero=175 tabs=42 toolbar=64 tableHead=41
计价规则    topbar=58 常驻新增表单=~420 tableHead=38
```

首屏平均数据行 **7.7**。一个每天盯 8–10 小时的调度员，看到的屏幕里一半以上不是数据。

## 七个具体问题

### 1. 壳子吃掉 28%–54% 的垂直空间

调度工作台顶上那条深色 hero 占 **175px**，里面是一个标题、一句说明、四个数字——其中三个是 0。一天看八小时，这 175px 每一秒都在那儿，信息量却是常数。

计价规则更极端：**542px（54%）** 的壳，因为"新增合同价"表单常驻展开。新增一条计价规则是一个月做一次的事，而看规则列表是每天做的事。频率和空间分配完全反了。

### 2. Chip 病：能分类的东西都做成彩色药丸

计价规则一行五个 chip：`应收` `按重量阶梯` `2级` `+5.0%` `启用`——而且"启用"列同时有勾选框和"启用"标签，两个都长得像能点。

订单表的状态列是 24px 高的填充药丸，宽度随文字变（`已转运单` 比 `草稿` 宽一倍）。药丸左边缘对齐但右边缘不齐，扫列的时候眼睛得逐个读文字，不能靠形状。专业台面上状态是「色点 + 文字」，色点固定位置，一眼扫出形状。

### 3. 一切都是浮卡

指标带、工具条、表格各自一张 12px 圆角卡，飘在米色底上，卡间 16px。加上 `.content` 的 `max-width:1600px` 居中和 20px padding，每屏白吃掉约 80px 纵向 + 左右各若干。

浮卡是消费级 dashboard 的语言——每张卡是一个"小部件"，适合十分钟看一眼。仪器台面的语言是边到边的窗格 + 1px 分隔线：屏幕是一块连续的工作面，不是一堆卡片的拼贴。

### 4. 侧栏 265px = 16% 的横向空间，放 8 个入口

8 个链接占掉六分之一的屏幕宽度。订单表有 11 列要挤在剩下的空间里。

### 5. 没有纵向分隔线

11 列、行宽约 1400px、行高 40px。没有列分隔线时，眼睛横向跟一行会掉行。这不是审美问题，是"看错行"的问题。

### 6. 一屏 51 个彩色元素

订单管理首屏：17 个蓝色单号链接 + 17 个彩色状态药丸 + 17 个蓝色 `B` 徽标。颜色用到这个密度就不再是信号——真正需要注意的东西（逾期、异常、超时）淹在里面。

颜色预算应该是稀缺的：一屏彩色元素控制在个位数，剩下全是墨色和灰。

### 7. 时间只有相对值

`11天前`、`12天前`。运营对账、查单、追责都要绝对时间。相对时间适合"3 分钟前"这种刚发生的事，`11天前` 既不精确又不好算。

## 判断

前面几轮我修的都是执行层缺陷（对比度、固定列透底、密度按钮失效、空占位符），审美方向没动——还是"暖瓷底 + 石墨侧栏 + 蓝青渐变 + 12px 圆角 + 柔阴影"。这套语言是给一天用十分钟的工具设计的。

给一天用八小时的台面，方向要换：**从"仪表盘"改成"仪器"**。

## 方向

1. **边到边窗格，去浮卡**：工作区不再居中限宽，取消卡间距、圆角、阴影，改 1px hairline 分割。
2. **色彩预算制**：状态改「色点 + 文字」，中性状态（已完成、草稿）不给颜色。彩色只留给要动作的。
3. **单一强调色**：去掉蓝→青渐变。渐变在仪器上是噪声。
4. **中性冷灰底**取代暖米色：低亮度、低饱和，不刺眼也不"温馨"。
5. **默认紧凑**：行高降一档，字号收进 12.5–13px 一档。
6. **加纵向列分隔线**（极淡）。
7. **绝对时间为主**，相对时间做副行。
8. **低频表单不常驻**：计价规则新增收进抽屉。
9. **侧栏瘦身**，把横向空间还给数据。

## 验收（可量化）

- 首屏平均数据行 7.7 → **≥ 14**
- 壳占比：订单 28% → ≤ 22%；调度 40% → ≤ 25%；计价 54% → ≤ 25%
- 一屏彩色元素 51 → ≤ 12
- 抽样文本对比度全部 ≥ AA(4.5)，暗色同样
- 亮/暗双主题无缺失 token（`src/test/tokens.test.ts` 守着）

## 两处我按研究结论改回了自己前一版的决定

做完第一轮后，两个研究 agent 的结论直接推翻了我的两个决定。记在这里，
因为它们都属于「听起来对、实际上没依据」那一类，很容易再犯：

**1. 我把表格正文压到 13px、次级信息压到 11px，方向错了。**
当时的理由是"密度靠压壳子，不靠缩字"——原则对了一半：默认档不该低于可读
下限，但我一边说不缩字一边把 `--text-xs` 留在 11px，还用在「31件」「时间戳」
这类真数据上。按 critical print size 换算，11px 在 24" 1080p @60cm 只有阈值
的 77%，已进入阅读速度陡降区。13px 是边界值；需要逐位核对的字段（单号、金额、
地址）下限应是 14px。
现在正文 13.5px、下限 12px，而且**三档密度同时缩放行高与字号**（32/13.5、
38/14、46/15）。后者是关键：密集表格在 13–14px 下本质是零余量运行，
所以字号必须是用户可切换项，而不是设计师定死的一个数。

**2. 我把工作面从纯白降到 #fbfbfc 来"减光晕"，这是没有依据的。**
现有实验里对比度越高阅读绩效越好、主观偏好也越高；"高对比度伤眼"缺乏实验
支持。被归因于"对比度过高"的不适实际来自**屏幕绝对亮度**——那是显示器设置
（建议约 120 cd/m²，环境照度 300–500 lx），不是 CSS 能管的事。
工作面已回到纯白，正文 `--ink` 也调深到 14.8:1。

顺带一条同类的：暖色底"护眼"也没有依据，现有实验里最暖的档位疲劳最高，
中性偏冷（色相 210–220°、饱和度 4–10%）最优。这一条我原本的方向是对的
（暖米色 → 冷中性灰），但理由当时只是"暖色读着像消费级"，属于蒙对。

# 再一轮：换一把更严的尺子，抓到 5 处第一把尺子量不到的东西

第一把尺子（`scripts/dev/ui-audit.mjs`）在浏览器里**取样**：量的是"这个元素此刻
所处的背景"。一行数据会经历六种底色——常态 / 表头 / 三级面 / hover / **选中** /
异常 tint——而取样只会碰到当时渲染出来的那一种。它每次都恰好量在白底上，
报 `--muted` 5.81，而同一个 token 在**选中行底**上只有 4.62。

第二把尺子（`src/test/contrast-matrix.test.ts`）改成纯计算：直接读 token 值，
把「每个承载信息的前景 × 十种可能背景」全枚举。不需要浏览器，跑在 CI 里。
外加 WCAG **1.4.11**（非文本 ≥3:1）——第一把尺子只算文字，根本没查边框。

一跑抓到 5 处：

| 问题 | 实测 | 修法 |
|---|---|---|
| 亮色 `--red` 在**选中行底**上 | 4.40 | `#c62b30 → #bd2429`，最差 4.84 |
| 暗色 `--muted` 在选中行底上 | 4.47 | `#8a92a1 → #949cab`，最差 5.06 |
| 输入框边框 `--line-2` 对白底（1.4.11 要 ≥3:1） | **1.50** | 拆出 `--ctl-line: #78818f`，最差 3.13 |
| 暗色 `--ctl-line` 在选中行/琥珀 tint 上 | 2.95 / 2.98 | `→ #767f8b`，最差 3.45 |
| 状态色点无描边，中性灰点对浅底 | **2.1** | 加 1px 同语义色 inset 描边 |

`--line-2` 那条是最典型的：一个 token 同时承担"结构分隔"（要淡）和"输入框边框"
（要 ≥3:1）两个互斥要求，88 处引用全在那个 1.50 的值上。拆成两档之后，
结构线保持安静，控件边界合规。

## 顺带发现：字重三档在中文界面上是假的

token 里写着 `--fw-medium: 550 / --fw-semibold: 640 / --fw-bold: 720`，
CSS 里另有 17 种不同的 `font-weight` 值。按 CSS 字重匹配规则，目标 ≥500 时
先向上找最近的可用字重——而 Windows 的微软雅黑只有 400/700 两个实例，
**550、640、720 全都落到 700**，三档编码等于一档。

实测（本机 CJK 回落字体）：400…800 八个字重下「运输管理系统对账」宽度
完全相同（159.33px），而拉丁走 Inter Variable 是连续变化的。

结论有两层。一是字重值收敛到标准四档 400/500/600/700（17 种 → 4 种），
非标准步进值在中文字体上是赌博。二是更重要的：**中文界面不能只靠字重编码
重要性**——字重做加强，颜色/位置/字号做主编码。

## 还有一个不是设计问题的问题

同一轮里发现调度台的行光标是 `useState(-1)` 的**数组下标**，而 `rows` 每次渲染
重跑 `sortUrgent`、三个池子都是 15 秒轮询。某单 SLA 翻成临期被顶到最前，
下面所有行下移一位，光标不动——高亮框还在原来那个 y，`Enter` 派出去的是
**另一张单**。

像素一个都没动，所以视觉审计一整轮都没看到它：尺子量的是像素，
而这里错的是"这个像素位置现在代表哪条记录"。已改成锚记录 id，
并加了 `src/test/cursor-identity.test.ts` 扫源码钉住。

# 第二轮：走查二级页面，发现的不是像素问题

第一轮把尺子对准了几个高频页（驾驶舱/订单/调度/对账）。二级页面一张张翻过去，
问题的性质变了——不再是"边框差 0.5 个对比度"，而是**整屏在说废话**。

## 两个「总览」页签，加起来两屏空白

`/fleet` 的默认落地页是「总览」：六张卡片写着 6 / 0 / 18 / 14 / 5 / 0，
下面 **840px 空白**。六个数分别是"承运商 / 线路价库 / 车辆 / 司机 / 客户 / 证件预警"——
和它旁边那六个页签的名字一一对应。每次进资源库都要先看一屏这个，再点一下才开始干活。

`/org` 的「运营总览」更糟：六个读数里四个是 0，加上两张各只有一行的分布表。
而且 `.kv` 是固定两列 + `space-between`，铺满 1490px 后每格 730px——
「组织总数」和它的「4」隔着近 700px 空白，虚线引线根本牵不住，
眼睛要横穿一整屏才能把标签和数字连起来。

数字本身有用：它告诉你哪个库是空的、值不值得点进去。**有用的位置是页签标签旁边**，
不是一整屏卡片。于是：

- 计数 → 页签角标（`.seg-n`，安静的灰色，不做填充徽标——那是"有 N 件事等你"的语汇）
- 页面直接落在能干活的那一页（承运商中心 / 组织架构）
- 「证件到期」「在职无账号」这类**待办**做成跨页签常驻的窄条：藏进某个页签等于没提醒
- 两张分布表删掉——组织架构树每行都带经营属性标签，服务区划表每行都带类型列，
  分布在原表里一眼可数，不需要另开一页复述

`.kv` 顺带给每格封了 360px 上限。

## 「管理后台」是一层纯中转

点进去是一整页，内容是两张链接卡片：「组织与权限」「审计日志」。
侧栏本来就是导航，再套一层导航，等于每次多点一下、多等一次加载。
两个目的地直接进侧栏，`/admin` 保留重定向（老书签仍可用），smoke 里显式测这条重定向。

## 尺子测不出、但一眼能看见的：折叠算法在不该折的时候折

承运商中心只显示了**两列**：承运商、城市。另外五列（类型/评级/账期/预警/状态）
被"单值列折叠"收进了工具栏 chip。

这个功能本身是对的——密集账本最缺横向空间，整页同值的列不值得占一列宽。
但它**无条件触发**。这张表 7 列声明宽合计 770px、容器 1488px，本来富余 718px，
根本不缺空间；六条演示数据恰好五列同值，于是五列全折，剩下两列被
`table-layout: fixed` 拉成 1026 + 462——右边 460px 全是空的。
工具栏那五个 chip 还长得和"已生效的筛选条件"一模一样，会让人以为表被筛过了。

**折叠是为了缓解拥挤；不拥挤时它只是在藏数据。** 改成先量后折：

1. 列声明宽合计没超过容器 → 不折
2. 折到只剩 3 列以下 → 不折（两列的表不是台账）

宽度用 `ResizeObserver` 实测；测到之前（首帧 / jsdom）按"不拥挤"处理——
宁可先都显示出来，也不要在没量之前就藏东西。两条守卫测试钉住这两条规则。

同一轮里还试过给经营指标的读数格封宽度上限（3 个指标铺满 1007px 时每格 335px，
内容只占左边 140px）。量下来不划算：`auto-fit` 的列数是按**上限**算的，
封 240px 得 4 列、封 260px 只剩 3 列，两种都会把原本一行放得下的 4 个指标逼折行，
面板反而高 24–40px。**留白比折行便宜**，所以宽度维持 `1fr`，结论写在代码里。
真正让读数散架的是涨跌幅被 `space-between` 甩到格子右边（离它注解的数 200px），
那个改成紧跟标签。

## 版面按频次排，不按 CRUD 排

组织架构 / 员工名录 / 服务区划三个页签，每页顶上都常驻一张展开的「新增 X」表单，
各占 160–230px，把真正要看的名录推到折叠线以下。

新增组织这种事一年做几次，看名录是每天做几十次。收成 33px 的触发条。
