# 界面审计：为什么现在这套不够专业

用 `scripts/dev/ui-audit.mjs` 在 1680×1000 下量的，不是看着觉得。下面每条都有数字。

## 基线数字（改版前）

| 页面 | 首屏数据行 | 行高 | 壳高 | 壳占比 |
|---|---|---|---|---|
| 订单管理 | 17 | 40px | 282px | 28% |
| 调度工作台 | 2 | 54px | 395px | 40% |
| 计价规则 | 4 | 56px | 542px | 54% |
| 驾驶舱 | — | — | — | 指标带 231px |

壳子构成（亮色）：

```
订单管理    topbar=58 stats=42  toolbar=64 tableHead=34
调度工作台  topbar=58 hero=175 tabs=42 toolbar=64 tableHead=41
计价规则    topbar=58 常驻新增表单=~420 tableHead=38
```

首屏平均数据行 **7.7**。一个每天盯 8–10 小时的调度员，看到的屏幕里一半以上不是数据。

## 七个具体问题

### 1. 壳子吃掉 28%–54% 的垂直空间

调度工作台顶上那条深色 hero 占 **175px**，里面是一个标题、一句说明、四个数字——其中三个是 0。一天看八小时，这 175px 每一秒都在那儿，信息量却是常数。

计价规则更极端：**542px（54%）** 的壳，因为"新增合同价"表单常驻展开。新增一条计价规则是一个月做一次的事，而看规则列表是每天做的事。频率和空间分配完全反了。

### 2. Chip 病：能分类的东西都做成彩色药丸

计价规则一行五个 chip：`应收` `按重量阶梯` `2级` `+5.0%` `启用`——而且"启用"列同时有勾选框和"启用"标签，两个都长得像能点。

订单表的状态列是 24px 高的填充药丸，宽度随文字变（`已转运单` 比 `草稿` 宽一倍）。药丸左边缘对齐但右边缘不齐，扫列的时候眼睛得逐个读文字，不能靠形状。专业台面上状态是「色点 + 文字」，色点固定位置，一眼扫出形状。

### 3. 一切都是浮卡

指标带、工具条、表格各自一张 12px 圆角卡，飘在米色底上，卡间 16px。加上 `.content` 的 `max-width:1600px` 居中和 20px padding，每屏白吃掉约 80px 纵向 + 左右各若干。

浮卡是消费级 dashboard 的语言——每张卡是一个"小部件"，适合十分钟看一眼。仪器台面的语言是边到边的窗格 + 1px 分隔线：屏幕是一块连续的工作面，不是一堆卡片的拼贴。

### 4. 侧栏 265px = 16% 的横向空间，放 8 个入口

8 个链接占掉六分之一的屏幕宽度。订单表有 11 列要挤在剩下的空间里。

### 5. 没有纵向分隔线

11 列、行宽约 1400px、行高 40px。没有列分隔线时，眼睛横向跟一行会掉行。这不是审美问题，是"看错行"的问题。

### 6. 一屏 51 个彩色元素

订单管理首屏：17 个蓝色单号链接 + 17 个彩色状态药丸 + 17 个蓝色 `B` 徽标。颜色用到这个密度就不再是信号——真正需要注意的东西（逾期、异常、超时）淹在里面。

颜色预算应该是稀缺的：一屏彩色元素控制在个位数，剩下全是墨色和灰。

### 7. 时间只有相对值

`11天前`、`12天前`。运营对账、查单、追责都要绝对时间。相对时间适合"3 分钟前"这种刚发生的事，`11天前` 既不精确又不好算。

## 判断

前面几轮我修的都是执行层缺陷（对比度、固定列透底、密度按钮失效、空占位符），审美方向没动——还是"暖瓷底 + 石墨侧栏 + 蓝青渐变 + 12px 圆角 + 柔阴影"。这套语言是给一天用十分钟的工具设计的。

给一天用八小时的台面，方向要换：**从"仪表盘"改成"仪器"**。

## 方向

1. **边到边窗格，去浮卡**：工作区不再居中限宽，取消卡间距、圆角、阴影，改 1px hairline 分割。
2. **色彩预算制**：状态改「色点 + 文字」，中性状态（已完成、草稿）不给颜色。彩色只留给要动作的。
3. **单一强调色**：去掉蓝→青渐变。渐变在仪器上是噪声。
4. **中性冷灰底**取代暖米色：低亮度、低饱和，不刺眼也不"温馨"。
5. **默认紧凑**：行高降一档，字号收进 12.5–13px 一档。
6. **加纵向列分隔线**（极淡）。
7. **绝对时间为主**，相对时间做副行。
8. **低频表单不常驻**：计价规则新增收进抽屉。
9. **侧栏瘦身**，把横向空间还给数据。

## 验收（可量化）

- 首屏平均数据行 7.7 → **≥ 14**
- 壳占比：订单 28% → ≤ 22%；调度 40% → ≤ 25%；计价 54% → ≤ 25%
- 一屏彩色元素 51 → ≤ 12
- 抽样文本对比度全部 ≥ AA(4.5)，暗色同样
- 亮/暗双主题无缺失 token（`src/test/tokens.test.ts` 守着）

预算按页面角色分档，不用一个数管到底：作业面（台账/工作台/表单）一天盯八小时，
颜色必须稀缺，上限 12；纵览面（驾驶舱）管理者看几分钟，它的本职就是告诉你
"哪里不对"，告警色与趋势色都是信息，上限放到 24。

这把尺子第一版自己有 bug：暗色主题量出 197 个"彩色元素"。因为我用了相对彩度
`(mx−mn)/mx`——深色中性灰 `#171a20` 算出来 0.28，看着像"28% 饱和"，实际只差
9/255 ≈ 3.5%，肉眼就是一块中性深灰，分母太小把它放大了。改用绝对色差
`(mx−mn)/255` 后两个主题量纲一致。

注：验收指标从「首屏实际数据行」改成了「首屏容量」。前者会被数据量拖低——
调度池只有 2 单、计价只有 4 条规则，量出来的是种子数据的多少，不是布局的好坏。

## 两处我按研究结论改回了自己前一版的决定

做完第一轮后，两个研究 agent 的结论直接推翻了我的两个决定。记在这里，
因为它们都属于「听起来对、实际上没依据」那一类，很容易再犯：

**1. 我把表格正文压到 13px、次级信息压到 11px，方向错了。**
当时的理由是"密度靠压壳子，不靠缩字"——原则对了一半：默认档不该低于可读
下限，但我一边说不缩字一边把 `--text-xs` 留在 11px，还用在「31件」「时间戳」
这类真数据上。按 critical print size 换算，11px 在 24" 1080p @60cm 只有阈值
的 77%，已进入阅读速度陡降区。13px 是边界值；需要逐位核对的字段（单号、金额、
地址）下限应是 14px。
现在正文 13.5px、下限 12px，而且**三档密度同时缩放行高与字号**（32/13.5、
38/14、46/15）。后者是关键：密集表格在 13–14px 下本质是零余量运行，
所以字号必须是用户可切换项，而不是设计师定死的一个数。

**2. 我把工作面从纯白降到 #fbfbfc 来"减光晕"，这是没有依据的。**
现有实验里对比度越高阅读绩效越好、主观偏好也越高；"高对比度伤眼"缺乏实验
支持。被归因于"对比度过高"的不适实际来自**屏幕绝对亮度**——那是显示器设置
（建议约 120 cd/m²，环境照度 300–500 lx），不是 CSS 能管的事。
工作面已回到纯白，正文 `--ink` 也调深到 14.8:1。

顺带一条同类的：暖色底"护眼"也没有依据，现有实验里最暖的档位疲劳最高，
中性偏冷（色相 210–220°、饱和度 4–10%）最优。这一条我原本的方向是对的
（暖米色 → 冷中性灰），但理由当时只是"暖色读着像消费级"，属于蒙对。

## 守卫

改完的结论都钉成了自动检查，不靠下一轮记得：

- `src/api/format.test.ts` — 空≠零、时间锁 Asia/Shanghai、`fmtDateShort` 契约，
  外加三条源码扫描（没有裸 `-` 占位符、时间不绕过 `fmtDateTime`、金额不手拼 `¥`）
- `src/test/tokens.test.ts` — 每个 `var(--x)` 都有定义；暗色不缺颜色 token
  （尺寸类 `--row-h-*` 已排除——`row` 这个词根同时命中颜色和尺寸，
  不排掉会把行高误报成"暗色缺的颜色"）
- `src/components/DataTable.test.tsx` — 中文按拼音序排、密度默认档是 compact
- `scripts/dev/ui-audit.mjs` — 密度、壳占比、对比度；对比度跌破 AA 时退出码非 0
- `scripts/dev/smoke-ui.mjs` — 十个页面的非 2xx 请求与未捕获异常
